# Making recall ten times faster (work of 29-30 October 2026)

On 29 October the goal was set to make every recall in the brain ten times faster and leaner, measured rather than
claimed: the same bank, the same machine state and the same queries before and after, with accuracy held. This page
records the plan, what landed and what did not. All timings were taken on one heavily loaded Windows laptop (commit
charge 86-93 percent, under 10 GB free on the system disk, a new shell taking 15-35 seconds to start), so they are
that machine's numbers, not the code's floor.

## Where it started

| Recall path | Before (27-29 Oct) | Target |
|---|---|---|
| Math store search, prepared state on disk | 24-60 s a call | 3-6 s |
| Math store search, reading the live store | 50-70 s, up to 200-380 s | 7 s |
| Building the prepared state | 1-3 h; 8 of 8 builds failed on a store that kept moving | 10 min, never failing |
| A new card becoming findable | hours (the next finished build) | 5 min |
| Tokens printed by one search | about 3,500 | about 350 for a first pass |
| General memory recall | timeouts at 400 s under memory pressure | 10 s |

The October tests had already settled the accuracy side: spreading one hop through the graph buys nothing (22 of
the bank either way at 4.5 times the cost), and hop-depth weights and per-session caps do not pay. Two or three
wordings in one call, and walking by id, are what raise accuracy. So the ten times had to come from speed and cost.

## The six leads

1. **A resident recall server** that holds the prepared state in memory so each call is a local request.
2. **An incremental side index**, so a new card is findable without a full rebuild.
3. **A build that cannot fail on a moving store**: read the store as one version.
4. **Codex warm start**: the recall tool started before the turn, with a long startup timeout and a health probe.
5. **A lean first pass**: one line per card, whole cards only on request.
6. **Profile general recall** and give it the same treatment.

## What landed

**Lead 2, the side index.** When the prepared state on disk is behind the store, the search loads it and indexes
only the cards it has not seen, in memory, before answering. The build stays the only writer of prepared states; if
the catch-up refuses or fails, the old behaviour runs, and a half-extended state is never served.

| | Before | After |
|---|---|---|
| 7 cards written 4-7 minutes earlier by other agents, each searched by its own title | 0 of 7 found | 7 of 7 at rank 1 |
| 9 older cards in the same run | 9 of 9 at rank 1 | 9 of 9 at rank 1 |
| Ingest to findable | the next finished build (20-40 min at normal priority, hours at low) | the first call after the write |
| Catching up on open | | 3.2 s for 7 cards |
| 1,000 newest cards removed, then re-added by the catch-up | | 40 of 40 searches identical to a full build; 15.8 s |
| 60 newest cards, including a superseding link | | 20 of 20 identical, exclusions equal |

When the state on disk is current the old code path runs unchanged, so bank answers cannot move. Installed, 8 of 8
bank searches were byte-identical with the catch-up on and off.

**Lead 3, one version of the store.** The build read nodes and then edges as separate statements, each its own
implicit read transaction, so a write landing between them gave an index built from two versions of the store (an
edge to a card missing from the node list, or a retraction applied to one half). The fix opens one read transaction
around both reads. On a copy of the store with a second connection inserting an edge between the two reads, the old
code saw the new edge both times (mixed versions) and the fixed code neither time. With no writer, both produce the
same nodes and edges, by count and by hash (90,850 nodes and 127,771 edges on the live store). Speed is unchanged.
The same lead moved the build from low to normal priority, which is what brought builds down to 20-40 minutes.

**Lead 6, general recall.** A profile of one call found the cost in the file system, not in ranking. The memory folder
holds about 37,500 files, and one recall listed or examined it up to four times; the cache built on top was keyed on
the folder's signature, which other agents change every few seconds, so it missed on nearly every call while the
signature itself took 3-5 seconds. In a stalled call, re-verifying and re-tokenizing every attached document took 118
of 155 seconds. What landed from it: one directory listing per recall, made with a single native directory scan and
shared by every part that needs it, the freshness check included; the same native scan in the embedding loader; a
supersession cache that no longer misses when a peer writes; and an index builder that stops itself when the
generation it is building has already been replaced. On the math side the vector file is now memory-mapped instead
of read whole.

The strength step of a math recall used to load the whole 150 MB vector file to read about 70 rows. Mapped, its peak new memory fell from 136 MB to 14 MB and the load from 14.5 s to 4.1 s in one profiled call, with the same similarities on all 302 card pairs checked. The 30-question math recall bank gave the same output on 30 of 30 questions before and after leads 2 and 3 and this change (the answer card printed for 11 of 30 each time, the same tokens on 28). Its median went from 28.2 s on the loaded machine to 8.4 s on a quiet one; the quieter machine accounts for about half of that, so the figure is not a speedup of the code alone.

**Lead 1, the resident server**, measured on 20 bank items, each call a fresh process: median 26.8 s cold against 7.4 s
through the server (3.6 times), output byte-identical on 20 of 20 with the same rank for the right card. It did not
pay in daily use. The server reloaded its prepared state whenever the store's key changed, and with other agents
writing the store all day the key changed under almost every call, so served calls ran 67-90 s against about 20 s
cold. A keeper now starts the server, probes it every ten minutes, and stands it down for an hour after two slow
probes, so it can no longer make recall slower. The fix it needs is lead 2's catch-up on a key change instead of a
full reload.

On 30 October a second cause turned up. After each store change the server reloaded and dropped its prepared state, but the old state sat in reference cycles, so the next call ended at about 1,820 MB against the server's 1,536 MiB cap and the server stopped itself, 23 to 40 minutes after each start, five times that day. A garbage collection in the store-change branch and before the cap check frees it (memory falls to about 1,050 MB), and every refusal now writes a reason code to a log. With the fix the server lived through two store changes and kept answering its probes in about 5 s. That is one afternoon on one machine, not yet a daily measurement.

The open-problem lookup had the same shape. A cache older than six hours made every call rebuild the index in the foreground, which on a loaded machine ran past the ten-minute limit, so the cache never refreshed and every call timed out. It now serves the stale index in about 5 s and rebuilds once in the background; most of the rebuild (about 570 of 790 s) is matching problem text against the store.

## What did not land

- **Lead 5, the lean first pass**, is measured for size only. One line per card is 7-8 times smaller than the full
  printout (about 300-430 tokens a search) and the existing list mode is 2.4-2.7 times smaller with the same hits in the
  same order. Printing less does not make the search faster. Its accuracy is unknown: snippets alone scored 34 of 100
  against 83 for whole cards in the October test, so a lean pass pays only if the agent then reads cards by id, and
  that needs a bank run.
- **Lead 4, the Codex warm start**, exists only inside the benchmark harness that launches Codex runs. An ordinary
  Codex session has no recall server entry in its configuration at all.
- **Showing a pinned hub at rank 2** instead of rank 1: one gain against two losses on 83 questions. Not landed.
- **Lifting a memory's successor** into the results hurt recall on the bank of questions in the user's own words. Not landed.
- **A third meaning-lane pick at rank 6**, beside the two that landed at ranks 4 and 5: hit@8 went from 75 to 76 of 99, three gains against two losses, and the one net gain is on the held-out set that helped choose the rule. No cosine threshold separated the gains from the losses. Not landed.
- **Putting the newer of two near-duplicate memories first**: at every word-overlap threshold that changed anything it cost answers (hit@1 on the user's own words 38 to 37). The older memory, or the correction it carries, is usually the answer. Not landed.

## Small accuracy change that landed

General recall fuses several lanes. On a held-out set of 16 questions, four misses were fusion losses: the lane that
scores by meaning alone had the answer in its top five, and the fused top eight dropped it. Recall now shows that
lane's own top two at ranks 4 and 5 unless the fused order already has them there or higher; ranks 1-3 never move.
Of 18 rules tried offline only this one lost nothing anywhere. End to end on 83 questions, hit@8 rose from 49 to 50 on
56 questions in the user's own words and from 7 to 9 on the 16 held-out ones (in-sample, since they helped choose the rule), with no
question losing its answer at any depth. A reader who stops at rank 3 sees no change.

## Accuracy check

The 29 October bank re-run at depth 0 after leads 2 and 3 landed held its earlier score.
Of the 30 items in that bank the right card was printed for 11 both times, the same 11, and 28 of the 30 printed the same
number of tokens. The run was not a speed test: the machine was under heavy load all evening.

## Where it stands

The ten times is not reached on the median warm call. What changed most is ingest to findable, from hours to the next
call, and the build, from failing on a moving store to finishing in 20-40 minutes. The resident server is the step
still missing, and it needs the catch-up on key change before it helps on a store that is written all day.
