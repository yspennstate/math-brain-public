## Exact mathematical contract

Let

\[
\Delta_3=\{x\in\mathbb R^4:x_i\ge0,\ \sum_i x_i=1\},\qquad
K=\{x\in\Delta_3:\max_i x_i\le2/5\}.
\]

The coefficient tensor must satisfy, for every index,

\[
P_{ij,k}=P_{ji,k}\ge0,\quad \sum_kP_{ij,k}=1,\quad
P_{ij,k}=0\text{ when }k\in\{i,j\}.
\]

These conditions include diagonal parent pairs and permit zero allowed
coefficients. For a rational candidate `x`, the finite certificate checks all
these conditions, exact membership `x in K`, and

\[
V_k(x)=\sum_{i,j}P_{ij,k}x_ix_j,\qquad
R=\sum_k|V_k(x)-x_k|,\qquad B=\min\{2,5R\}.
\]

Every value in those calculations is rational. Stochasticity gives

\[
\sum_kV_k(x)=\sum_{i,j}x_ix_j\sum_kP_{ij,k}
            =\left(\sum_i x_i\right)^2=1.
\]

Nonnegativity gives `V(x) in Delta_3`. Every fixed point `y` obeys

\[
y_i\le(1-y_i)^2,\qquad
y_i\le c:=\frac{3-\sqrt5}{2}<\frac25.
\]

The first inequality uses the parental-output prohibitions and `P_{ij,k}<=1`.
The quadratic has only its smaller root in `[0,1]`; the strict comparison with
`2/5` follows from `sqrt(5)>11/5`. Thus the true fixed point lies in the cap used
for the emitted intervals, including boundary fixed points.

### Why the factor five certifies error

For `T=(3/5)I+(2/5)V`, Theorem 2 of the supplied note gives the l1 contraction
factor `L=23/25` on `K`, with its unique fixed point `x*` there. Hence

\[
\begin{aligned}
\|x-x^*\|_1
&\le \|x-T(x)\|_1+\|T(x)-T(x^*)\|_1\\
&\le \frac25 R+\frac{23}{25}\|x-x^*\|_1.
\end{aligned}
\]

Rearranging, with `1-L=2/25`, gives `||x-x*||_1 <= 5R`. The simplex has l1
diameter two, so `B=min(2,5R)` remains an upper bound. The solver uses the
residual of **V**, not the residual of **T**. Multiplying the residual of `T`
by only five would omit the factor `1/(2/5)` and would be incorrect.

I checked this deduction and the exact constants against the supplied theorem.
This audit does not constitute a formal verification or a fresh independent
proof of every line of Theorem 2. The record verifier checks its finite
arithmetic premises and conclusion format; the mathematical error conclusion
still depends on that analytic theorem.

### Why each coordinate gets half the l1 bound

For any zero-sum real vector `z`, let `P={i:z_i>0}` and `N={i:z_i<0}`. Then

\[
\sum_{i\in P}z_i=-\sum_{i\in N}z_i
                 =\frac12\sum_i|z_i|.
\]

If `z_i>=0`, its value is at most the total positive mass; otherwise its
absolute value is at most the total negative mass. Therefore

\[
|z_i|\le\frac12\|z\|_1\quad\text{for every }i.
\]

Apply this to `z=x-x*`, whose coordinates sum to zero because **both** points
are probability vectors. It follows that

\[
x_i^*\in\left[
\max(0,x_i-B/2),\ \min(2/5,x_i+B/2)
\right].
\]

The factor `1/2` is sharp for the zero-sum argument alone: e.g. the difference
between `(3/10,1/5,1/4,1/4)` and `(1/5,3/10,1/4,1/4)` is
`(1/10,-1/10,0,0)`. Both vectors lie in `K`. This does not claim sharpness of
the solver's overall residual constant. Also, `B/2` is the **unclipped** radius;
the displayed interval can be shorter or asymmetric after clipping at zero
and `2/5`.

### Stronger agent 013 denominator versus the implemented safe bound

Agent 013 derives, using the actual fixed-point cap `c`,

\[
\|x-x^*\|_1\le
\min\left\{2,\frac{R}{1-c-\|x\|_\infty}\right\}
\quad\text{when }\|x\|_\infty<1-c.
\]

For `x in K`, its denominator is at least `3/5-c`, which is strictly larger
than `1/5`. The associated uniform multiplier is

\[
\frac1{3/5-c}=\frac{25\sqrt5+45}{22}<5.
\]

Thus the root solver's multiplier five is conservative, not erroneous. It
does **not** implement the stronger denominator from agent 013. Neither the
original nor my hardened copy claims that it does.

One must not insert a rounded floating-point value of `c` into an alleged
exact rational upper bound without controlling the rounding direction. An
optional entirely rational improvement is to use `c_bar=191/500>c`, justified
by `(559/250)^2<5`. Then

\[
\frac{R}{1-c-\|x\|_\infty}
\le \frac{R}{1-191/500-\|x\|_\infty},
\]

with a positive rational denominator on `K`; its uniform multiplier is
`500/109<5`. This observation was derived algebraically, not implemented or
claimed as an optimal constant. The supplied stronger inequality itself is
agent 013's proof, not a new theorem claimed by worker 026.

## Input and serialization audit

### Original command-line parsing: passed

`validate_pairs` builds a `4 x 4 x 4` tensor of `Fraction` objects from exactly
the ten unordered pairs, rejects duplicate pairs, requires integer indices
with `0<=i<=j<4`, copies parent-symmetric rows, checks four coefficients per
row, and checks exact nonnegativity, unit row sum, and forbidden zeros.

Probability values accept integers or strings and explicitly reject booleans
and JSON floating-point numbers. Thus an unquoted JSON scientific number
such as `0e0` is rejected, while a quoted string such as `"2.5e-1"` is parsed
exactly. `"-0"` is the exact rational zero, not an error. Nonfinite JSON values
and strings cannot become valid coefficients. A denominator-zero string is
rejected by `Fraction` via `ZeroDivisionError`, which the command-line wrapper
catches as an `ArithmeticError`. Missing required row fields produce a caught
`KeyError`; there is no certificate output in that case.

The tested scientific-string row `['-0','2.5e-1','2.5E-1','+5e-1']` became
exactly `[0,1/4,1/4,1/2]`. Eight targeted invalid-input mutations were rejected
by both original and hardened coefficient parsers; exact case names and errors
are in the execution JSON.

The default JSON decoder still applies its ordinary handling of duplicate
object keys, and additional object fields are ignored. I did not change those
policies or treat them as a proof failure: certification concerns the operator
actually returned by parsing. The embedded canonical operator in the hardened
record makes that interpreted operator visible. It does not preserve the raw
input's byte-level provenance.

### Largest-remainder normalization: passed

For four finite nonnegative search values, not all zero, the original function
first converts each binary float to its exact rational value. If `p_i` are
these values normalized by their exact rational total and `D=10^digits`, set
`n_i=floor(D*p_i)` and `r=D-sum(n_i)`. Since `sum(D*p_i)=D`,

\[
r=\sum_i(Dp_i-\lfloor Dp_i\rfloor)\in\{0,1,2,3\}.
\]

Adding one to the `r` largest remainders makes `sum(n_i)=D` exactly. All
numerators remain nonnegative. Dividing by `D` therefore produces a rational
probability vector. Ties are resolved deterministically by lower index. The
subsequent cap comparison is exact and is an independent necessary check;
normalization by itself does not establish the cap.

The isolated tests verified this property at digits 1, 12, and 30, at the cap,
for subnormal search values, and for finite search values whose ordinary float
sum overflows. The latter still succeeds because the normalization total is
formed from exact fractions. The patched public helper additionally checks
vector length, allowed numerical input types, integer digit range, and the
remainder invariant before returning a result. These are interface checks;
the original `solve` already supplies four floats and an allowed CLI digit
count.

### Search underflow does not corrupt an exact certificate: passed

In a separate allowed row, a coefficient supplied as `"1e-400"` is retained
exactly as `10^-400`; its search-only float is zero. At the uniform candidate,
the independently recomputed exact residual was

\[
R=\frac1{24}-\frac1{8\cdot10^{400}},
\]

including the term lost by float conversion. The original solver met its
default tolerance at search step 16 for that input, and its returned record
passed the independent rational verifier. This verifies independence of the
certificate from that specific real underflow event, not a universal theorem
about floating-point search convergence.

### Public API flaw 1: false zero certificate, reproduced

Start with `equiprobable_input()` and replace its `(0,0)` row by

\[
\left(0,\frac13+\delta,\frac13-\delta,\frac13\right),
\qquad\delta=10^{-20}.
\]

This row and the full operator satisfy every exact coefficient condition. At
`u=(1/4,1/4,1/4,1/4)`, changing that row changes two output coordinates by
`+delta/16` and `-delta/16`, because its input weight is `(1/4)^2=1/16`.
Consequently `R=delta/8>0` exactly and `u` is not fixed.

Calling the original `certify(P,[.25]*4)` nevertheless produced candidate
strings `['0.25','0.25','0.25','0.25']`, residual `"0.0"`, error upper
`"0.0"`, and singleton coordinate intervals at `0.25`. Multiplication of a
`Fraction` coefficient by a float coordinate changes the subsequent arithmetic
to floating point, losing the perturbation. The record still claims
`"exact rational residual; floating-point candidate search"`.

The independent verifier rejected the record because its residual differs
from exact recomputation. The hardened `certify` rejects these float inputs
before any candidate arithmetic. Calling the original `certify` with four
`Fraction(1,4)` coordinates instead gives the correct exact residual and bound.
This confirms that the main CLI path, which uses fraction candidates, is not
affected by this particular flaw.

### Public API flaw 2: serialized candidate need not be normalized, reproduced

For the invariant-triple operator, the original direct call with
`[1/3,1/3,1/3,0.0]` passes the float `sum(x)==1` check. Its emitted candidate
strings sum, as exact rationals, to

\[
\frac{9999999999999999}{10000000000000000}\ne1.
\]

Thus the exact-simplex premise and hence the zero-sum justification are not
established for the serialized candidate. The independent verifier rejects
that record. This is another effect of the same missing exact-type check;
it is fixed at the same API boundary.

### Public API flaw 3: settings do not meet the advertised exact contract

The original `solve` accepts tolerance `True`, positive infinity, NaN, and an
ordinary finite float. It emits respectively `"True"`, `"inf"`, `"nan"`, or
the decimal rendering of the float as `requested_tolerance`. The first three
cannot denote a positive exact rational tolerance. NaN makes both the initial
positivity rejection and the success comparison false, producing a misleading
failure flag rather than input rejection. Positive infinity yields success.
The original also accepts booleans as digits or maximum steps because Python
booleans are integers in comparisons and exponentiation/range operations.

These cases do not invalidate the CLI, whose tolerance comes from the exact
string parser and whose integer controls come from argparse. They do break
the public API's uniform exact-settings contract. The patched API accepts
only built-in `int` or `Fraction` tolerances, rejecting `bool` and every float,
and requires actual integers for the two integer controls.

### Coefficient-array API preconditions and record binding

The original `certify` docstring explicitly presupposes an array returned by
`validate_pairs`. Consequently handing it an arbitrary malformed or mutated
array violates a stated precondition; that is not the same category as the
demonstrated float-candidate bug. Nevertheless, a reliable public certificate
entry point should establish its own finite hypotheses. The isolated copy's
`validate_array` checks shape, exact coefficient types, nonnegativity,
stochasticity, parent symmetry, and parental-output prohibitions, returning a
copied exact array. Both `solve` and `certify` enforce it. Focused tests rejected
an exactly stochastic but asymmetric array and a floating coefficient array.

The original JSON record does not contain its coefficients or a coefficient
identifier. It is verifiable only together with the intended external input.
This is a portability/provenance limitation rather than an arithmetic flaw.
The isolated copy adds:

```text
certificate_schema: "four-type-qso-residual-v1"
operator: {pairs: [the ten canonical rational rows]}
cap: "2/5"
```

The independent verifier parses these coefficients without importing either
solver's parsing, evaluation, or certification routines. It evaluates the
operator using the ten unordered pairs with a factor of two for distinct
parents, independently of the solver's sixteen ordered-pair summation. When
given an external operator too, it verifies equality with the embedded one.
It rejects altered residuals, l1 bounds, interval endpoints, caps, prohibited
offspring rows, and substitution of a different external operator. It also
rejects an original record presented without its required external input.

## Stopping, epsilon, and actual exact-oracle outcomes

With exact positive tolerance `epsilon`, the solver parses the serialized
bound back into a `Fraction` and sets success only when the exact comparison
`B<=epsilon` holds. The returned `best` candidate has a bound no greater than
the currently tested candidate. Therefore success implies

\[
\|x_{\mathrm{returned}}-x^*\|_1\le B\le\varepsilon.
\]

The inclusive comparison is correct at equality. If the step limit is reached
without success, the solver returns the best certified candidate with
`tolerance_met=false`. That means the requested bound has not been certified;
it does not imply that the candidate's actual error exceeds the requested
tolerance. The command-line return code is 0 for success and 2 for a completed
search that did not certify the tolerance. Parser/input errors also use
argparse's status 2, but produce an error diagnostic instead of a success
record. Both status behaviors were exercised for original and isolated copies.

`max_steps=0` intentionally still certifies the initial candidate. At digit
count 1, the uniform floating search state rounds to
`(3/10,3/10,1/5,1/5)`. For the equiprobable operator the exact residual is
`1/3`, so `B=5/3`. Tests confirmed success at tolerance `5/3`, failure at
`5/3-10^-100`, and retention of step zero as the best candidate after a longer
unsuccessful coarse-grid search.

The float search is explicitly heuristic. Fixed finite digit count and finite
step budget do **not** guarantee that every positive requested epsilon will
be reached. In the digit-one example the search state is uniform at every
iteration, the rounded candidate stays the same, and the requested tolerance
`1/10` cannot be met by this run. Its actual error is `1/5`. This is expected
honest failure, not a certificate defect.

The two existing exact fixed-point oracles passed independent evaluation,
certificate recomputation, serialization round trips, l1 error checks, and
coordinate-interval containment. Their existing output fields are identical
between the original and hardened solver:

| Operator | Exact fixed point | Search step | Actual l1 error | Certified l1 bound |
|---|---|---:|---|---|
| Equiprobable | `(1/4,1/4,1/4,1/4)` | 0 | `0` | `0` |
| Invariant triple | `(1/3,1/3,1/3,0)` | 38 | `29/15625000000` | `29/3125000000` |

For the boundary oracle, the exact residual also equals `29/15625000000`.
The default tolerance was met in both cases. A rational candidate exactly on
the `2/5` cap was accepted; exceeding the cap by `10^-30`, while maintaining
exact normalization, was rejected.
